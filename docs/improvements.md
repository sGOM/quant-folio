# QuantFolio 개선점 정리

백엔드 리팩토링 로그(`docs/refactoring-backend.md`), financial-expert 자문 로드맵, 코드 내 보류 주석.

> 2026-07-10 전체 코드 리뷰에서 확정된 17건(High 2·Medium 5·Low 3·프론트 3·DB 4)은 **전부 수정 완료**,

## 1. 백테스트 방법론 — financial-expert P2 로드맵 (미착수)

P0(익일종가 체결·슬리피지, KOSPI200 벤치마크·alpha/beta/IR)와 P1(팩터 IC/IR 성과귀속,
리스크 레이어, 사이즈 중립화)은 완료. 남은 것:

- **P2-1 과최적화 통계 방어**: Deflated Sharpe Ratio 등으로 다중 실험(전략 후보 탐색) 후
  살아남은 전략의 통계적 유의성을 검증. 현재는 튜닝된 파라미터(예: id=23 레짐 exit 0.15)가
  과최적화인지 판별할 장치가 없음.
- **P2-2 거래비용·유동성 정밀화**: ADV(일평균거래대금) 대비 주문 규모 캡, 정수 주 단위 체결.
  현재 슬리피지는 bp 고정 + 변동성 스케일뿐이라 소형주·대규모 자금에서 비용이 과소평가됨.
- **P2-3 실거래–백테스트 정합 실측**: 모의투자 러너가 돌고 있으므로, 실제 체결가와 백테스트
  가정(익일 종가 + 5bp)의 괴리를 주기적으로 측정·리포트하는 파이프라인 필요.

## 2. 리스크 관리 — 라이브 미적용 항목

- **MDD 킬스위치의 실거래 러너 적용**: 현재 백테스트 전용(계좌 HWM 상태를 러너가 지속
  보관해야 해서 보류됨). 라이브에서 파국 방어가 없는 상태이므로, 계좌 고점을 DB/Redis에
  영속화해 러너에도 배선하는 것이 우선순위 높음.
- **섹터 집중 한도**: 신뢰할 수 있는 종목→섹터 매핑 소스 부재로 보류
  (`backend/app/schemas/strategy.py:460` — pykrx 업종 구성종목 API가 빈 값 반환).
  KRX 로그인 세션(krx_index)이나 OpenDART 산업분류로 매핑 소스를 확보하면 해제 가능.
  집중 한도·변동성 타겟팅과 달리 섹터 쏠림은 현재 무방비.

## 3. 데이터 계층

- **pykrx/FDR 의존 취약성**: 이 환경에서 불안정함이 반복 확인됨(종목명 해석은 이미
  krx_index로 이관). 팩터 계산(`metrics/fetch.py`)의 펀더멘털·등락률 조회도 여전히 pykrx
  의존 — 전면 장애 가드는 있으나(리밸런싱 스킵), **일별 시세·펀더멘털의 자체 적재
  (price_ticks 하이퍼테이블 활용)로 외부 API 실시간 의존을 줄이는 것**이 근본 대책.
  현재 price_ticks 스키마는 있으나 백테스트·팩터 계산이 이를 데이터 소스로 쓰지 않음.
- **KRX 로그인 세션 만료 대응**: PIT 지수구성 조회가 KRX_ID/PW에 의존 — 인증 실패 시
  `config.universe` 고정 폴백으로 조용히 전환됨. 폴백 발생을 사용자에게 알리는 경보 필요
  (생존편향 검증 원칙상 PIT 유니버스 이탈은 치명적).

## 4. 인프라 · DevOps

- **CI 부재**: `.github/workflows` 없음. 백엔드 223+건 pytest·프론트 `tsc --noEmit`/lint를
  PR마다 자동 실행하는 GitHub Actions 추가가 저비용·고효과. 현재는 머지 차단 룰셋만 있고
  테스트는 수동 실행에 의존.
- **핫리로드 부재**: web/engine/worker 코드 변경 시 수동 `docker compose restart` 필요.
  개발 compose 프로파일에서 `uvicorn --reload`·`watchfiles` 도입 검토(운영 프로파일과 분리).
- **엔진 관측성**: 러너 상태·틱 성공/실패·PIT 폴백·팩터 조회 스킵 등이 로그로만 남음.
  최소한 엔진 헬스 지표(마지막 성공 틱 시각, 연속 실패 횟수)를 대시보드에 노출하고,
  임계 초과 시 알림으로 연결.

## 5. 제품 기능 (PRD 대비 미구현)

- **알림(이메일/푸시)**: PRD에서 "추후"로 분류된 채 미구현. 자동매매 특성상 체결·리스크
  한도 도달·엔진 정지·MDD 킬 발동은 즉시 알림이 필요 — 관측성 항목과 묶어 처리 권장.
- **실전 투자 전환 절차**: 현재 모의투자 검증 단계. 실전 전환 전 체크리스트
  (P2-3 정합 실측 결과, 주문 금액 상한, 수동 승인 플로우 등)를 문서화·구현할 필요.
- **다중 전략 동시 운용 검증**: 러너 구조는 다중 전략을 지원하나, 동일 종목을 복수 전략이
  들고 있을 때의 포지션 귀속·리스크 한도 합산이 검증되지 않음.

## 6. 테스트 · 품질

- **프론트엔드 테스트 0건**: 백엔드는 pytest 커버리지가 두터운 반면 프론트는 타입체크뿐.
  최소한 `lib/`의 포맷·계산 유틸(손익 색상, 숫자 포맷)과 핵심 훅에 vitest 단위 테스트 권장.
- **엔진 통합 테스트**: 러너 단위 테스트는 있으나, "시세 수신→신호→리스크→주문→체결
  기록" 종단 경로를 모의 브로커로 검증하는 통합 테스트가 없음.

## 7. 소소한 정리

- `frontend/tsconfig.tsbuildinfo`, `sh.exe.stackdump`(루트·frontend) 등 산출물이 작업트리에
  존재 — `.gitignore` 등재 여부 점검.
- 전략 검증 결과가 세션 메모리·docs에 분산 — `docs/strategies.md`에 전략별(특히 id=23/24)
  판정 기준(alpha/Sharpe vs excess/IR)과 최신 검증 수치를 일원화하면 재검증 시 혼선 방지.
