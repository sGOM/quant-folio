## 1. 전략 라이프사이클 가드 — 잔존 포지션 무결성 (최우선)

`DELETE /strategies/{id}`(`strategies.py:388`)가 **잔존 포지션 확인 없이 즉시 삭제**한다.
FK가 `ondelete="SET NULL"`이라 삭제 순간 해당 전략의 Position/Order/Execution이
전부 `strategy_id=NULL`(비귀속)로 바뀐다.

- 문제 1 — **유령 포지션**: 미청산 포지션이 비귀속으로 남아 어떤 러너도 관리하지 않게 됨.
  계좌 잔고에는 보이지만 매도 신호를 낼 주체가 없다.
- 문제 2 — **NULL 중복**: `uq_positions_user_strategy_symbol`에서 NULL은 서로 다른 값으로
  취급되므로(Postgres), 삭제를 반복하면 같은 (user, symbol)의 비귀속 포지션이 여러 행 쌓일 수 있다.
- 문제 3 — **가동 중 삭제 레이스**: 엔진이 해당 전략 러너를 돌리는 중에 삭제되면
  러너의 다음 조회가 빈 결과를 보게 됨.

구현 방향:
- 미청산 포지션(qty>0) 존재 시 삭제 거부(409) + "먼저 청산 또는 이관" 안내.
- 엔진 가동 중(활성 러너 존재) 삭제 거부 — Redis 러너 상태 키로 확인.
- 선택: 비귀속(NULL) 포지션 점검·정리용 관리 스크립트(중복 병합·수동 귀속).

## 2. KIS 실시간 체결통보 연동 — 즉시체결 가정 제거

`engine/executor.py` 주석 그대로 "시장가 주문 접수를 **즉시 체결로 간주**"하는 단계에 머물러 있음
(정밀 체결 통보 연동은 5단계로 예약). 모의투자에선 무해하나 실전에선:

- 부분체결·미체결이 실제로 발생 — 즉시체결 가정은 Position 수량·평단을 왜곡.
- reconcile(주기 재조회)이 보완 중이지만 폴링 지연 동안 리스크 계산이 낡은 포지션을 봄.

구현 방향:
- KIS 실시간 체결통보 WebSocket(H0STCNI0/H0STCNI9) 구독 → `record_fill` 단일 진입점으로 반영.
- 접수 시점엔 PENDING 유지, 통보 수신 시 체결 확정 — reconcile은 유실 보완용 2차 방어선으로 강등.
- §1 게이트의 정합 실측(M1/M3)도 실제 체결가 기반으로 정확해지는 부수 효과.
- 실전 전환 전 마지막 남은 큰 현실성 격차.

## 3. 전략별 리스크 분리 후속 (§3에서 의도적으로 미룸)

PR #49에서 포지션은 분리했으나 리스크 집계는 계좌 단위로 남겨둠(주석으로 명시).

- `_daily_pnl`(`engine/risk.py`) — 일일 손실 한도가 계좌 합산. id=23+24 병행 시 한 전략의
  손실이 다른 전략의 주문까지 차단(현 설계 의도이나, 전략별 한도 옵션이 있으면 유연).
- `RiskLimit`은 이미 per-strategy 필드가 있으므로 배선만 남음 — 전략별 일일 한도가
  설정된 경우 전략 스코프 집계를 추가로 검사(계좌 한도는 유지, AND 조건).
- 비귀속(strategy_id=NULL) 포지션의 리스크 귀속 규칙 명문화(계좌 단위에만 포함).

## 4. 슬리피지 캘리브레이션 프론트 노출 (§2 백엔드만 완료)

승인 API는 있으나 UI가 없어 승인이 curl 수동 호출임.

- 기존 정합 리포트 카드(#44)에 제안값(`현재 → 제안 slippage_bps`)·근거 표본수 표시.
- "적용" 버튼 → 확인 다이얼로그 → `POST .../apply` — 409(제안 불일치) 처리 포함.
- 백엔드가 재계산·검증하므로 프론트는 표시·확인 흐름만.

## 5. 프론트 테스트 확대 — 훅·컴포넌트

vitest 기반은 갖춰짐(@testing-library 설치 완료). 순수 유틸 다음 단계:

- `lib/strategy.ts`의 `summarizeConfig`/`formatNode` 등 전략 요약 로직.
- TanStack Query 훅(모킹된 fetch로 상태 전이), WebSocket 재연결 훅.
- 핵심 표시 컴포넌트(손익 색상·등급 배지) 렌더 테스트.
