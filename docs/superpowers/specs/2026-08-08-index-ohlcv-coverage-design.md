# 지수 OHLCV 구간 커버리지 조회 설계 (2026-08-08)

## 1. 배경

로컬 영구 저장소(§49, PR #118)의 조회 게이트는 페치 원장(`external_fetches`)의
**캐시키 정확일치**다. 날짜 단위 키를 쓰는 소스(펀더멘털·시가총액·전종목 OHLCV·PIT
지수구성)는 이것으로 충분하지만, **범위 키를 쓰는 소스는 요청 범위가 한 글자라도
다르면 미스**가 된다. 이미 받아 테이블에 쌓아 둔 행이 있어도 원장이 그 키를 모르면
못 믿고 다시 받는다.

§49 는 이 한계를 "구간 커버리지 기반 조회는 별도 과제"로 남겨 두었다. 이 문서가 그
과제의 설계다.

## 2. 목표와 비목표

**목표(가용성)**: pykrx 가 막힌 상태에서도 **이미 받아 둔 구간에 들어오는 조회는
로컬로 굴러가야 한다.** 값은 속도가 아니라 가용성이다 — 레짐·패닉·벤치마크가 지수
OHLCV 에 의존하므로, 이 조회가 막히면 백테스트가 통째로 선다.

**비목표 — 기간 통계(`stock_period_stats`)는 대상이 아니다.** 등락률·누적 순매수는
`[start, end]` **구간 자체가 값**인 집계라, 긴 구간을 갖고 있어도 짧은 구간을 뽑아낼
수 없다. 구간 커버리지가 원리적으로 성립하지 않는다. 일봉(`stock_daily_snapshots`)
에서 유도하는 방법은 있으나 pykrx 가 보고하는 값과 수치가 갈릴 수 있어 이 설계의
범위 밖으로 둔다.

따라서 **대상은 `index_ohlcv` 하나**다. 나머지 소스는 이미 날짜 단위 키라 이 문제가
없다.

**비목표 — 성능 최적화가 아니다.** 같은 인자로 반복하는 경로(같은 백테스트 재실행,
하루 안의 반복 틱, `compute_panic_series` 의 구간 1회 조회)는 지금도 캐시가 듣는다.
이 작업이 여는 것은 **범위가 밀리는 반복 조회**(워크포워드 폴드, 날짜가 바뀌는 일일
호출)와 **선적재된 넓은 구간의 재사용**이다.

## 3. 핵심 결정

### 3.1 커버 구간은 "받아온 행의 범위"가 아니라 "요청한 범위"다

`[A, B]` 를 달라고 해서 pykrx 가 정상 응답했다면 그 창 안의 데이터는 전부 받은
것이다 — 행이 몇 개든, 중간에 휴장일이 며칠이든. 그래서 커버 구간으로 **요청 범위를
그대로** 기록한다.

이 결정이 **거래일 달력 의존을 없앤다.** 저장된 행의 최소/최대 날짜로 커버리지를
추론하는 방식은 중간 갭(휴장일인지 미적재인지)을 가릴 수 없어 조용히 불완전한 지수
시계열을 서빙하게 된다 — §47 재발 형태다. 그 접근은 기각한다.

### 3.2 저장된 커버 구간은 정의상 전부 확정분이다

원격 조회 `[A, B]` 성공 시 `covered_to = min(B, last_final_date())` 로 잘라
기록한다. 잘린 결과가 `A` 보다 이르면 아무것도 기록하지 않는다. 당일 봉은 장중 계속
변하므로 애초에 커버리지에 들어가지 않는다 — 별도 `final` 컬럼이 필요 없다.

### 3.3 빈 결과는 커버리지로 기록하지 않는다

pykrx 가 빈 응답을 준 것은 "명시적으로 데이터가 없다고 선언한 것"이 아니다(스키마
변동으로 값을 잃었을 수도 있다). §49 가 코어 원칙으로 올린 `row_count == 0 →
final=False` 와 같은 판단을 여기서도 적용한다.

### 3.4 겹치거나 맞닿은 구간만 병합한다 — 주말 갭은 병합하지 않는다

새 구간 `[N, M]` 을 넣을 때, 같은 지수의 기존 구간 `[F, T]` 중

```
N <= T + 1일  AND  F <= M + 1일
```

를 만족하는 행들을 모두 골라(양방향 조건 — 한쪽만 보면 새 구간이 기존 구간보다
앞설 때 병합이 누락된다) 새 행 `[min(F…, N), max(T…, M)]` 하나로 대체한다.
`covered_from` 이 PK 의 일부이므로 병합은 **선택된 행 삭제 후 삽입**으로 구현한다.

금요일에 끝난 구간과 월요일에 시작하는 구간(+3일)은 **병합하지 않는다** — 그 사이에
거래일이 있었는지 달력 없이 단정할 수 없다. 보수적으로 두 행으로 남긴다.

대가는 병합이 덜 되는 것뿐이고, 잘못 병합해 없는 구간을 커버됐다고 주장하는 쪽이
비교할 수 없이 위험하다.

### 3.5 부분 커버여도 전 구간을 다시 받는다

빠진 구간만 골라 받아 합치는 방식은 pykrx 비용이 **호출당이지 행당이 아니라서**
얻는 것이 없고 병합 로직만 늘린다. 커버리지는 **완전 포함일 때만** 원격을 건너뛴다.

### 3.6 커버 밖 요청이 실패하면 보유 구간을 알려주되 자동 축소하지 않는다

요청이 커버 밖이고 원격도 실패하면 `DataSourceError` 를 그대로 올리되, `detail` 에
로컬 확보 구간을 덧붙인다.

```
[krx] 지수 OHLCV 조회 실패(1001 20200101~20260801): ...
      — 로컬 확보 구간: 2020-01-01~2025-06-30
```

**커버된 구간으로 백테스트 기간을 자동 축소하지 않는다.** 기간이 조용히 바뀐 성과를
같은 것으로 착각하는 함정은 이 저장소가 이미 데인 적이 있다(§ id=23 초과수익이 구간
변경 아티팩트였던 건). 축소는 사람이 명시적으로 한다.

## 4. 데이터 모델

```
index_ohlcv_coverage
  index_code    varchar(20)   PK
  covered_from  date          PK
  covered_to    date          not null
  updated_at    timestamptz   not null default now()
```

`(index_code, covered_from)` 복합 PK. 한 지수에 여러 행이 있을 수 있다(3.4 의 미병합
구간). 저장된 모든 구간은 확정분이다(3.2).

**원장과의 관계**: `index_ohlcv` 는 이제 `external_fetches` 를 쓰지 않는다. 범위형
소스에서 원장이 하던 일("미적재 vs 데이터 없음")을 커버리지 테이블이 더 정확히
한다. 둘을 병행하면 진실이 두 곳이 된다. 마이그레이션에서 `source='index_ohlcv'`
원장 행을 삭제한다.

## 5. 조회 흐름

`frame.py` 에 `cached_range()` 를 `cached_frame()` 의 형제로 둔다. 계약이 한 모듈에
모여 있어야 `docs/CONVENTIONS.md` 의 "조회 진입점은 `cached_frame` 하나" 서술이
참으로 유지된다(그 문장은 "범위형은 `cached_range`" 를 더해 갱신한다).

```
요청 [A, B]
 ├ B > last_final_date() ────────────────→ 원격 (당일분은 로컬로 못 준다)
 ├ [A,B] 를 포함하는 커버 구간 있음 ─────→ read_local() 반환, 외부 접촉 0
 └ 그 외 ────────────────────────────────→ 원격
      ├ 성공 → write_local() → merge_coverage(A, min(B, last_final_date()))
      │         (빈 결과면 커버리지 기록 안 함 — 3.3)
      └ 실패 → 같은 예외 클래스로 재구성, detail 에 보유 구간 첨부 (3.6)
```

주입 스타일은 `cached_frame` 과 동일하다(`read_local`·`fetch_remote`·`write_local`).
원장 대신 `read_coverage`·`merge_coverage` 를 받는다.

**예외 재구성 전제**: `errors.py` 의 예외 계층이 전부 `(source, message,
retry_after=)` 시그니처를 공유한다(`DataSourceError.__init__`). 이 전제 위에서
`type(e)(e.source, 새_메시지, retry_after=e.retry_after) from e` 로 재구성한다.
쿨다운·실패 집계는 `_remote()` 안에서 이미 기록되므로 인스턴스를 바꿔도 영향 없다.

**메시지 형식**: 구간이 여럿이면 최신순 3개까지, 넘으면 `…외 N건`. 없으면 `없음`.

## 6. 정합성 장치

- **`last_final_date()` 단일 출처**: `frame.py` 에 두고 `is_final_date()` 가 그것을
  쓰게 한다. 두 곳에서 따로 계산하면 언젠가 어긋난다.
- **`delete_index_ohlcv()` 가 커버리지도 함께 지운다.** 행만 지우고 커버리지가 남으면
  "커버됐다는데 행이 없는" 상태가 되고 그게 곧 영구 빈 결과다. 마이그레이션 0015 가
  고친 것과 같은 형태의 함정이라 같은 함수 안에서 묶는다.

## 7. 야간 넓은 구간 선적재

커버리지만 넣으면 "겹치는 구간을 우연히 받아뒀을 때" 듣는다 — 운에 기대는 가용성이다.
목표(2절)를 실제로 달성하려면 넓은 구간을 미리 확보해야 한다.

`worker.ingest_daily_snapshots` 에 지수 OHLCV 단계를 되살린다. §49 I4 에서 이 단계를
뺀 이유는 **하루치 키(`(ymd, ymd)`)라 넓은 범위를 쓰는 소비자와 절대 겹치지 않아서**
였고, 커버리지가 그것을 정확히 해소한다.

- **구간**: `[_approx_start(대상일, 400, buffer=30), 대상일]`. 대상일은 기존과 같이
  KST 전날(확정분). 400 거래일이면 섹터(252)·레짐(`ma_period+10`, 기본 210)·패닉(90)
  소비자를 모두 덮는다.
- **대상 지수**: 코드가 상수로 갖고 있는 기준지수의 합집합 — `panic._INDEX_TICKER`
  (1001·2001), `rebalance_runner._REGIME_INDEX_TICKER`(1001·2001),
  `backtests._BENCHMARK_TICKER`(1028 포함), `factors.compute_residual_momentum` 의
  기본 `market_ticker`(1028). 즉 **1001·2001·1028** 세 개. 구현 시 그 상수들을 읽어
  재확인한다(업종지수는 대상이 아니다 — 수십 개라 비용이 크고 섹터 로테이션 전용).
- **실패율 분모**: 단계가 4 → 7 로 늘어난다. `_INGEST_FAILURE_ALERT_RATIO`(10%)는
  그대로 두되, 1건 실패가 1/7≈14% 로 여전히 임계를 넘는다는 점을 docstring 에
  유지한다(현재 "4개뿐이라 1/4=25%" 서술을 갱신).

## 9. 테스트

| 층 | 검증 |
|---|---|
| `cached_range` 단위 | 완전 포함 → 원격 호출 **0회** / 부분 커버 → 원격 1회 후 병합, 다음 호출은 히트 / `end` 가 오늘 → 커버리지 있어도 원격 / **빈 결과 → 커버리지 미기록**, 다음 호출도 원격 |
| 실패 경로 | 원격 실패 시 예외 **클래스가 보존**되고 `detail` 에 보유 구간이 실린다 |
| 병합 규칙(실 DB) | 겹침 병합 / 인접(+1일) 병합 / **주말 갭(+3일) 미병합** / `delete_index_ohlcv` 가 커버리지까지 삭제 |
| 배선 회귀 | 워크포워드 시나리오 — `[A,C]`·`[B,D]` 를 받은 뒤 `[B,C]` 요청이 원격 **0회** |
| 배치 | `_snapshot_steps` 가 7단계이고 지수 3종이 **넓은 구간**으로 호출된다(하루치가 아니다) |
| 마이그레이션 | 0016 upgrade/downgrade 왕복 |

모든 테스트는 실 KRX/DART/KOFIA 를 타지 않고 실 DB 에 행을 남기지 않는다
(`docs/CONVENTIONS.md` "테스트 격리"). 회귀 테스트는 대상 코드를 되돌렸을 때 실제로
실패하는지 확인하고 완료를 보고한다.

## 10. 롤백과 최악의 경우

커버리지 테이블이 비면 모든 조회가 미스가 되어 **현행 동작(매번 원격)으로 자연
저하**한다. 새 실패 모드를 만들지 않는다.

**"롤백" 이 뜻하는 두 가지를 갈라 적는다(2026-08-08 통합 리뷰가 재현·정정)**:

- **테이블 행만 삭제**(`DELETE FROM index_ohlcv_coverage`)는 안전하다. `read_coverage()`
  가 빈 목록을 돌려주고 `_covers([])` 는 항상 `False` 이므로 모든 요청이 미스 →
  원격으로 자연 저하한다. 위 문단이 말하는 것은 이 경우다.
- **마이그레이션 다운그레이드(테이블 자체를 DROP)를, 코드는 이 브랜치인 채로**
  실행하면 다르다. 이 경우 `read_coverage()` 가 존재하지 않는 테이블을 조회해 원시
  SQLAlchemy 예외(`ProgrammingError` 등)를 던지는데, 이 예외는 `cached_range` 어디서도
  잡히지 않고 그대로 호출자까지 뚫고 올라간다. `DataSourceError` 계열로 분류되지
  않으므로 `app/main.py` 의 502/503 변환 대상도 아니다 — 처리되지 않은 예외로
  터진다.
  코드는 고치지 않는다: 정상적인 롤백 절차라면 코드(이 브랜치의 revert)와 스키마
  (마이그레이션 다운그레이드)가 **함께** 되돌아가므로 이 불일치 상태 자체가
  일어나지 않는다. 코드만 남기고 스키마만 먼저 지우는 것은 배포 절차를 어긴
  비정상 상태이고, 그 상태에서 원장 SQL 예외가 조용히 흡수되지 않고 시끄럽게
  터지는 쪽이 이 저장소의 철학과 맞는다(§48/§49 가 반복해서 요구하는 "실패를 값으로
  삼키지 않는다"의 연장) — 여기서 `except Exception: return []` 류로 삼켰다면 다음
  조회가 다시 원격으로 저하하는 대신, 정합이 깨진 스키마 위에서 매 요청이 예외를
  던지는지조차 모른 채 넘어갈 위험이 더 크다.

## 11. 남은 한계

- **기간 통계는 여전히 정확일치 조회다**(2절). 이 설계로 해소되지 않는다.
- **업종지수는 선적재 대상이 아니다.** 섹터 로테이션은 pykrx 차단 시 여전히 멈춘다.
- **주말 갭 미병합**(3.4)으로 커버 구간이 실제보다 잘게 쪼개질 수 있다. 요청이 그
  경계를 걸치면 미스가 난다 — 안전을 위해 감수하는 비용이다.
- 최초 적재는 여전히 외부 가용성에 달려 있다. 이 설계는 **한 번이라도 받아 둔 구간**의
  가용성을 지킬 뿐, 받은 적 없는 구간을 만들어내지 못한다.
- **`cached_range` 는 "정상 응답 = 요청 창 전체 수신"을 코드로 검증하지 않고 그대로
  믿는다(2026-08-08 통합 리뷰).** §3.1 은 이 전제를 근거로 커버 구간을 "받아온 행의
  범위"가 아니라 "요청한 범위"로 기록하기로 결정했는데, `cached_range`(`frame.py`)의
  구현은 `fetch_remote()` 가 예외 없이 비어있지 않은 프레임을 돌려주기만 하면 —
  실제로 그 창을 다 채웠는지 확인하지 않고 — `merge_coverage(start, min(end,
  final_through))` 로 요청 범위 전체를 커버로 기록한다. 소스가 넓은 요청에 조용히
  일부만 잘라 응답하는 경우, 이 전제가 깨진 채로 커버리지가 기록된다: 그 구간
  전체가 확보로 기록됨 → 이후 미수신 하위 구간을 조회하면 로컬 히트로 판정되어 빈
  프레임 반환 → `_fetch_index_ohlcv` 의 `return out if not out.empty else None` 때문에
  "그 구간엔 원래 데이터가 없다"는 정상 상태와 구분이 안 됨 → 프로세스 재시작으로도
  회복되지 않고, 해당 지수의 커버리지·행을 통째로 지우는 것 외엔 무효화 수단이 없는
  영구 조용한 실패가 된다(§47 재발 형태).
  이 환경은 KRX 인증이 막혀 있어 pykrx 의 `get_index_ohlcv` 가 실제로 넓은 요청을
  부분 응답하는지는 **미확인**이다 — 확정할 수 있는 것은 "코드에 그 상황에 대한
  방어가 없다"는 사실뿐이고, "오늘 이 경로가 실제로 트리거된다"는 별개의(미확정)
  주장이다. 인증 재개 후 실측이 필요하다.
  **반환 행의 min/max 로 클램프하는 방어는 틀린 방향이다.** 요청 구간은 달력일
  (`[A, B]`)인데 실제 데이터는 거래일에만 존재한다 — 예를 들어 요청 시작이 1월 1일
  (휴장일)이면 첫 행은 1월 2일부터 시작해, 정상적으로 전 구간을 받았어도 min/max 는
  요청보다 며칠 좁게 나온다. 이 값으로 커버리지를 클램프하면 거의 매번 "실제로는 다
  받았는데 좁게 기록"하는 과소 주장이 되어 커버리지가 사실상 항상 미스로 동작한다
  (이 설계가 얻으려던 가용성 이득이 사라진다). 유효한 방어는 행 수 기반 휴리스틱
  이다 — 예: "수신 행 수가 그 구간의 기대 거래일 수(대략 달력일 × 5/7 - 공휴일
  추정) 대비 현저히 적으면 커버리지를 기록하지 않고 경고 로그를 남긴다." 다만 이건
  동작 변경(추정 로직 추가)이라 이 설계·브랜치의 범위 밖이며, 별도 후속 과제로
  남긴다.

  의 `cached_range` 는 소스 불가지 원칙을 지켜 `merge_coverage(start, end, row_count)`
  로 행 수를 전달만 하고 판단하지 않는다. 판단은 도메인 지식이 있는 호출부

  행 수가 기대치의 절반 미만이면 커버리지 기록을 건너뛰고 경고 로그를 남긴다. 상세는
