# 하루 만에 QuantFolio 이해하기 (완전 입문자용)

> 대상: **FastAPI도 모르고, 이 프로젝트 코드도 처음** 보는 사람.
> 목표: 오늘 하루 앉아서 이 문서를 위에서 아래로 따라가면 "이 앱이 뭘 하고,
> 코드가 어디서 어떻게 도는지"의 지도가 머릿속에 생기는 것.
>
> 이 문서는 **읽는 순서와 실습**만 안내한다. 깊은 이론은 같은 폴더의
> `01`~`08` 문서로 링크로 넘긴다. 이론서를 먼저 다 읽지 말고,
> **이 문서 순서대로 필요할 때 해당 문서만 펼쳐 보는 것**을 권한다.

---

## 이 앱이 하는 일 (30초 버전)

국내 주식(KRX)으로:

1. **백테스팅** — "이런 규칙으로 사고팔았으면 과거에 수익이 어땠을까"를 과거 데이터로 시뮬레이션.
2. **자동매매** — 그 규칙(전략)을 실제로 한국투자증권(KIS) API에 연결해 24시간 자동으로 주문.

화면(웹)에서 전략을 만들고 → 백테스트 돌려보고 → 마음에 들면 "실시간 ON" 하면
엔진이 알아서 매매하는 그림이다.

---

## 큰 그림: 프로세스가 여러 개다 (여기가 제일 중요)

보통 웹 앱은 "서버 하나"지만, 이 앱은 **역할이 다른 프로그램 여러 개가 동시에 돌고**
서로 **Redis**라는 중간 다리로 대화한다. Docker Compose가 이걸 한 번에 띄운다.

| 프로그램 | 하는 일 | 비유 |
|----------|---------|------|
| `web` | 화면이 부르는 API 서버 (로그인, 전략 저장, 시세 조회) | 일반 백엔드 서버 |
| `engine` | 장중 24시간 도는 자동매매 데몬 | 혼자 도는 로봇/배치 |
| `worker` | 시간 오래 걸리는 작업(백테스트 계산) 대신 처리 | 뒤에서 무거운 일 하는 일꾼 |
| `frontend` | 사용자가 보는 웹 화면 (Next.js) | 화면 |
| `db` | PostgreSQL, 데이터 저장 | 데이터베이스 |
| `redis` | 위 프로그램들 사이의 메시지·큐·잠금 | 사내 메신저 + 순번표 |
| `proxy` | 요청을 알맞은 곳으로 라우팅 (Caddy) | 안내데스크 |

> **왜 나눴나?** 매매 엔진은 절대 멈추면 안 되는데, API 서버는 자주 재배포된다.
> 둘을 한 프로세스에 두면 배포할 때마다 매매가 끊긴다. 그래서 떼어놨다.
> → 자세히: [`02-architecture.md`](02-architecture.md)

**핵심 감각 하나만 챙기자: web은 매매를 직접 하지 않는다.**
web은 "전략 켜줘"라는 신호를 Redis로 던지고, 실제 주문은 engine이 낸다.

## 오늘의 순서 (이 순서대로 하세요)

### STEP 0 — 일단 띄워본다 (약 20분)

코드를 읽기 전에 돌아가는 걸 눈으로 봐야 감이 온다.

```bash
docker compose up -d --build      # 전부 빌드+기동
docker compose ps                 # 7개가 떠 있는지 확인
docker compose exec web alembic upgrade head   # DB 테이블 생성(최초 1회)
```

그리고 브라우저에서:

- <http://localhost:8080/docs> ← **여기를 제일 먼저 보세요.**
  이게 **Swagger UI**. web 서버가 제공하는 **모든 API 목록이 자동으로 그려진 화면**이다.
  각 항목을 펼치면 "이 주소로 뭘 보내면 뭐가 돌아온다"가 다 나온다.
  코드 읽기 전에 이걸로 "이 앱엔 이런 기능들이 있구나"를 눈으로 훑는 게 제일 빠르다.
- <http://localhost:8080/health> ← 서버·Redis 살아있는지 JSON으로 확인.

로그를 흐르게 켜두고 화면을 만지면 이해가 빠르다:

```bash
docker compose logs -f web       # API가 불릴 때마다 여기 찍힘
docker compose logs -f engine    # 전략 ON 하면 신호/주문이 여기 찍힘
```

> Docker가 낯설면: [`08-docker-containers.md`](08-docker-containers.md)

### STEP 1 — FastAPI가 뭔지 감만 잡기 (약 30분)

FastAPI는 파이썬 웹 프레임워크다. **"이 주소로 요청 오면 이 함수 실행"**을
데코레이터로 붙이는 방식이다. 딱 이 감각만 있으면 코드가 읽힌다.

```python
@app.get("/health")      # GET /health 로 요청이 오면
async def health():      # 이 함수를 실행하고
    return {"status": "ok"}   # 이 딕셔너리를 JSON으로 응답
```

지금 이 코드가 실제로 `backend/app/main.py:101` 에 있다. 한번 열어서 확인해보자.

`main.py`에서 볼 것 세 가지만:
- **`app = FastAPI(...)`** — 서버 본체 생성 (37번째 줄).
- **`app.include_router(...)`** — 기능별로 나눠둔 API 묶음들을 서버에 등록 (88~98줄).
  `auth`(로그인), `strategies`(전략), `backtests`(백테스트), `trading`(매매)… 이름만 봐도 감이 온다.
- **`@app.get("/health")`** — 가장 단순한 API 예시.

> 스프링을 아는 사람이면 번역표: [`03-fastapi-for-spring-developers.md`](03-fastapi-for-spring-developers.md)
> (몰라도 됨. `@app.get` = "이 URL 담당 함수" 라는 것만 알면 진행 가능.)

---

### STEP 2 — 실제 기능 하나를 끝까지 따라가기 (약 40분)

가장 이해가 빨리 되는 방법: **API 하나가 요청부터 응답까지 거치는 길**을 따라가는 것.
"전략 목록 조회"를 예로 잡자.

열 파일: `backend/app/api/routes/strategies.py`

- 파일 맨 위 `router = APIRouter(...)` — 이 파일은 전략 관련 API들의 묶음.
- `@router.get(...)` 함수들이 각각 하나의 API.
- 함수 인자에 있는 `db`, `current_user` 같은 것들이 **의존성 주입**이다.
  "이 함수 실행 전에 DB 연결과 로그인된 사용자를 자동으로 준비해서 넣어줘"라는 뜻.
  그 준비 로직은 `backend/app/api/deps.py` 에 있다.

이 흐름(요청 → 인증 → DB → 응답)의 전체 그림: [`04-request-lifecycle.md`](04-request-lifecycle.md)

**직접 해보기:** Swagger(`/docs`)에서 전략 관련 API를 "Try it out"으로 눌러보고,
동시에 `docker compose logs -f web` 로그에 뭐가 찍히는지 대조해보자.

---

### STEP 3 — 데이터가 어떻게 생겼나 (약 30분)

앱이 다루는 "명사"들을 알면 전체가 잡힌다. DB 테이블 정의를 보자.

열 파일: `backend/app/models/models.py` (약 300줄, 부담 없음)

여기서 클래스 하나 = 테이블 하나다. 대충 이런 것들이 있다:
- `User` — 사용자
- `Strategy` — 매매 전략 (규칙, 종목 유니버스 등)
- `Backtest` — 백테스트 실행 결과
- `Order` / `Execution` — 주문과 체결
- `Position` — 현재 보유 종목

각 클래스의 필드(컬럼) 이름만 훑어도 "이 앱이 뭘 저장하는지" 지도가 그려진다.

> 설정값(환경변수·시크릿)이 어디서 오나 궁금하면: `backend/app/core/config.py`

### STEP 4 — 자동매매 엔진의 심장 (약 40분, 이 앱의 핵심)

여기가 이 프로젝트에서 가장 특별하고 조심스러운 부분이다. **실제 돈이 오간다.**

큰 흐름은 항상 이 3단계다:

```
신호(Signal) → 리스크 점검(Risk) → 주문(Order)
 "뭘 살까"      "사도 되나"        "실제 주문"
```

열 파일 순서:
1. `backend/engine/main.py` — 엔진 프로세스의 시작점.
2. `backend/engine/runner.py` — 전략을 주기적으로 돌리는 루프.
3. `backend/engine/risk.py` — 손절·포지션 한도 등 안전장치.
4. `backend/engine/executor.py` — 실제 주문을 KIS로 내보내는 곳.

**꼭 이해할 개념 2개:**
- **멱등성(idempotency)** — 같은 주문이 실수로 두 번 나가면 안 된다. 이걸 막는 장치가 곳곳에 있다.
- **분산 락(distributed lock)** — 엔진이 두 개 떠도 같은 주문을 중복으로 내지 않게 Redis로 잠근다.

> 자세히: [`05-trading-engine.md`](05-trading-engine.md)
> 실제 주문 흐름 참고: [`docs/live-order-guide.md`](../docs/live-order-guide.md)

⚠️ 이 부분 코드를 만질 때는 반드시 **모의투자(paper trading)** 환경에서.
`/health` 응답의 `paper_trading: true` 를 확인하는 습관.

### STEP 5 — 백테스트와 전략 (약 30분, 도메인)

"과거였으면 얼마 벌었나"를 계산하는 부분.

열 파일: `backend/app/services/backtest/engine.py`

가장 조심할 함정 하나: **미래참조(look-ahead bias)**.
"오늘 종가를 보고 오늘 아침에 샀다고 계산"하면 현실엔 불가능한 사기 수익이 나온다.
이걸 피하는 게 백테스트 정확성의 핵심이다.

> 이론: [`06-backtesting-and-signals.md`](06-backtesting-and-signals.md)
> 전략별 수식·근거(아주 상세): [`docs/strategies.md`](../docs/strategies.md)

## 막힐 때 팁

- **코드 고쳤는데 반영이 안 돼요** → engine/worker는 자동 리로드가 없다.
  `docker compose restart engine` 처럼 재시작해야 한다. web은 개발 환경에선
  `docker-compose.override.yml`이 자동 병합되어 `--reload`로 뜨므로 즉시 반영된다
  (운영 배포는 `docker compose -f docker-compose.yml up -d`로 override 제외).
- **에러가 어디서 났는지 모르겠어요** → 해당 서비스 로그부터.
  `docker compose logs -f web` (또는 engine/worker).
- **API가 뭘 받는지 모르겠어요** → 코드보다 `/docs`(Swagger)가 빠르다.
- 시크릿은 `.env`가 아니라 `secrets/*` 파일로 관리된다. **이 파일들은 커밋 금지.**
